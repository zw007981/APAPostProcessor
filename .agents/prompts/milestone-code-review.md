## 适用场景

Review Agent 对某个已提交开发结果的 Milestone 进行审查时使用（首次评审或后续每一轮复审均适用）。

## 前置阅读

- [docs/architecture.md](../../docs/architecture.md) —— 系统设计文档
- [docs/interfaces.md](../../docs/interfaces.md) —— 核心接口契约
- `docs/milestones/milestone-{N}/spec.md` —— 本 Milestone 的任务书与验收标准
- `docs/milestones/milestone-{N}/review-log.md` —— **必须通读全部历史轮次**，确认本轮要验证哪些上一轮提出的问题

> 编号 `{N}` 的确定方式：若人工在本次对话中已明确指定 Milestone 编号，以人工指定为准；否则读取 [docs/milestones.md](../../docs/milestones.md) 中「当前 Milestone（默认编号指针）」一节的默认编号。
- [.agents/instructions/cpp-style.md](../instructions/cpp-style.md)
- [docs/known-limitations.md](../../docs/known-limitations.md) —— 避免把已知的历史坑当新问题提出

## 角色设定

你是一位拥有丰富经验的资深软件架构师和 Tech Lead。你的代码审查以严谨、客观、富有建设性著称。你**只做只读审查，不修改任何代码文件**。

## 任务目标

请对本 Milestone 的代码进行全面的 Code Review。结合 `spec.md`、`docs/architecture.md`、`docs/interfaces.md` 与编程规范，严格按照以下五个维度进行深度分析，并给出具体的修改建议。

## 审查维度

1. **需求对齐 (Design Alignment)**：对比 `spec.md` 与 `docs/architecture.md`，逐一核对功能是否全部实现；明确指出是否有遗漏的业务逻辑或偏离原始设计的实现；如涉及 `docs/interfaces.md` 中的冻结接口，核对签名是否一致。
2. **代码逻辑与健壮性 (Logic & Robustness)**：
   - 排查潜在的 Bug、死循环、空指针/悬空引用/迭代器失效等致命错误；检查边界条件处理是否完善（空输入、单点/退化输入、极端规模输入），异常捕获是否合理，是否遵循 `.agents/instructions/cpp-style.md` 中"卫语句 + 抛出标准异常"的规范，而不是静默吞掉错误或返回魔法错误码。
   - **浮点与数值稳定性**：浮点数比较是否使用了容差而非直接 `==`/`!=`；是否存在潜在的 `NaN`/`Inf` 传播路径（除零、对负数开方、病态/奇异矩阵求逆、累积误差放大等）；若某个字段/返回值用特殊值（如 `NaN`、某个越界哨兵）表示"缺失/未定义/无效"，核对调用方是否先做有效性判断再使用，避免把哨兵值当作真实数值参与后续计算。
   - **迭代/求解过程的失败路径**：涉及迭代求解、优化、拟合、收敛类算法的代码，是否显式处理了"未收敛/达到最大迭代次数/求解失败/结果不可信"的分支，调用方是否有对应的降级或报错路径，而不是默认假设一定会成功。
   - **外部依赖的隐含契约**：调用第三方库、底层数据结构（如稀疏矩阵格式）时，是否严格遵守其文档/接口要求的隐含约束（如输入顺序、维度匹配、内存布局假设），并通过测试验证这些约束被满足，而不是仅凭经验假设"应该没问题"。
   - **坐标系/单位一致性**：涉及坐标系转换、角度与弧度、不同度量尺度换算的地方，是否有清晰注释说明约定，是否存在可能被上游误用的隐式假设。
3. **代码规范与可维护性 (Code Quality & Style)**：对照 [.agents/instructions/cpp-style.md](../instructions/cpp-style.md) 逐条核对（命名、访问控制、空行密度、异常处理等），不要凭经验判断；检查代码重复度（DRY）、函数/类复杂度。
4. **性能与计算效率 (Performance & Efficiency)**：
   - 分析核心算法的时间/空间复杂度，是否存在可优化到更低阶复杂度的实现；指出内存泄漏风险、冗余循环、不必要的对象创建（尤其是热路径中的堆分配与临时对象拷贝），核查是否遵守 cpp-style.md 中"提前 `reserve`""能 `constexpr` 就不放到运行时"等约束。
   - **重复计算与缓存**：是否存在可缓存却被重复计算的中间结果，循环内是否有可以提到循环外的不变量计算（loop-invariant hoisting）。
   - **数据结构选型**：容器/矩阵等数据结构的选择是否与问题实际规模和访问模式匹配，是否有本可利用某种结构特性（如稀疏性、局部性）却退化为更低效实现的地方。
   - 如 `spec.md` 要求 benchmark，核对压测结果是否达标，并关注是否存在偶发性能抖动（某些输入规模或数据分布下退化为最坏情况复杂度）。
5. **测试完整性 (Testing Coverage)**：
   - 评估单元测试（`test/*.t.cpp`）是否覆盖核心逻辑（Happy Path）以及异常/边界分支（Sad Path）；断言是否严谨（浮点比较是否用了容差），Mock/Stub 使用是否合理；是否遵循"每个测试用例上方用中文注释说明测试场景、触发原因与预期行为"的约定。
   - **退化与极端输入**：是否覆盖了空输入、单点/共线/退化几何、极小或极大规模参数、零/边界值输入，以及数值下溢上溢附近的临界值。
   - **失败路径**：是否覆盖了"求解失败/不收敛/输入非法"等负向路径的测试，而不仅是成功路径。
   - **测试脆弱性 (Test Brittleness)**：是否存在依赖多个参数精心耦合才能触发特定分支的测试；如存在，是否有清晰注释说明构造意图，避免默认值变化后测试静默失效或误报。
   - **可重复性**：涉及随机性或多次迭代的测试是否固定随机种子/采用确定性输入，保证结果可重复、不 flaky。

## 输出要求

- 结构化输出，严格按上述 5 个维度分点回答，不要遗漏。
- 指出问题时必须引用具体代码行或函数名，并给出具体的优化建议。
- 问题分级：
  - `🚨 阻断`：导致系统崩溃、严重 Bug 或偏离核心需求，必须修改。
  - `⚠️ 严重`：性能隐患或逻辑缺陷，强烈建议修改。
  - `📝 建议`：代码风格或可维护性优化，供参考。
- **必须将本轮完整结论追加到** `docs/milestones/milestone-{N}/review-log.md`（新增一个 `## Round {N} — 日期 — Review Agent` 小节，不覆盖历史内容），并在结尾写明"结论：🚨=x，⚠️=y，是否收敛"。
