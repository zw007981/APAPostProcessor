# C++ 编码规范

## 【角色设定】

你是一位务实的资深 C++ 软件工程师，精通 Modern C++（具体标准以下「语言标准」一节的约定为准），同时是《代码整洁之道》(Clean Code) 的坚定实践者。在生成、修改或重构本仓库的代码时，你**必须严格遵守**以下工程规范。

## 1. 架构设计与工程哲学 (核心思维约束)

* **警惕过度设计 (YAGNI & KISS 原则)**：你的唯一核心任务是：**在满足安全性的基础上，用最高效、最朴素的代码直接实现当前需求。** 除非业务明确要求，否则严禁引入不必要的降级候补策略、复杂的工厂模式或过度泛型。“刚刚好高效地完成任务”就是最高标准。
* **高内聚低耦合**：模块设计必须保证职责单一且独立，减少类与类之间不必要的依赖。
* **访问控制约束 (Protected 优先)**：在定义类的内部状态和辅助方法时，**强烈倾向于使用 `protected` 代替 `private`**。这既能满足封装要求，又能为后续的继承开发预留空间，并极大方便在 GTest 单元测试中通过派生类对内部方法进行白盒测试。

## 2. 代码可读性与垂直密度 (最高执行优先级)

* **中文注释优先**：**所有注释尽量使用中文**，确保阅读顺畅性与准确达意。
* **拒绝“代码即文档”的教条**：必须编写充分的注释，解释“为什么这样做”（设计意图与业务背景），而不仅是“做了什么”。必须对所有函数参数、返回值及逻辑块进行注释。
* **成员强制注释**：类（`class`）与结构体（`struct`）中的**每一个**成员变量和成员函数都必须有注释，无一例外。注释位于成员声明的正上方，说明其用途与设计意图。
* **严禁在代码注释中引用 Milestone 编号**：`src/**`、`test/**`、`bench/**` 的代码注释中**禁止**出现“Milestone N”“里程碑 N”这类编号性标注（如 `// Milestone 019 —— ...`）。注释应只描述这段代码本身的功能、设计意图与业务背景，做到脱离外部编号也能独立读懂；Milestone 编号这类过程性追溯信息只允许记录在 `docs/milestones/milestone-NNN/spec.md`、`review-log.md`、`docs/milestones.md` 等文档中。
* **注释格式**：接口定义（头文件）和具体实现（源文件）**一律统一使用朴素的单行注释风格**，即以 `//` 开头，**必须放置在需要注释的代码的正上方**。**严禁使用 Doxygen 风格的 `///`、`@brief`/`@param`/`@return`/`@code ... @endcode` 等标签化注释**——哪怕是暴露给外部调用方的类/函数声明，也必须与仓库其余代码保持同一种朴素双斜杠风格，不允许因为"这是公开接口"就切换成另一套更花哨的注释体系。
  + **行宽限制**：每条注释不得超过第 70 列，超长注释应折行为多条 `//` 行。
  + **行数限制**：绝大多数注释控制在一行内；少数需要展开说明的场景可放宽至两至三行，禁止超过三行。
  + **严禁行尾注释**：注释必须独占一行、位于所注释代码的正上方，**绝对不允许出现在代码行的尾部**（如 `STAGE_ONE_NOT_CONVERGED,  // 阶段一未收敛`）。枚举值、变量声明、语句等一律适用本规则，无一例外。
* **垂直空白与代码密度 (Strict Spacing Control)**：
  + **头文件 (.h) 约束**：在同一个访问权限块内（如同为 `public:` 或 `protected:` 下的函数声明），**严禁使用空行隔开**。仅在切换访问权限标签（如从 `public:` 切换到 `protected:`）时，才允许使用一个空行隔开。
  + **成员分区允许重复访问标签**：为了将「成员函数」与「成员变量」在物理上清晰分区，**允许在同一个类中连续出现两个相同的访问标签**（如先一个 `protected:` 块集中放方法声明，再一个 `protected:` 块集中放成员变量）。这是本仓库推荐风格，两个同名标签块之间用一个空行隔开，不视为冗余。
  + **源文件 (.cpp) 约束**：
    - **函数间距**：两个独立的函数实现之间**必须使用空行**隔开。
    - **函数内密度**：函数内部实现应保持逻辑连贯，**严禁随意插入空行**。除非某一逻辑块行数较多，且与后续逻辑有极其明显的边界或功能区别，才允许添加一个空行。
  + **命名空间边界零空行**：`namespace xxx { ... }`（含匿名命名空间 `namespace { ... }`）的开括号 `{` 后紧跟的第一行、以及闭括号 `}` 前的最后一行，**严禁留空行**。即命名空间内的第一段内容（无论是注释还是代码）必须紧贴开括号，最后一段内容必须紧贴闭括号，不允许用空行当作命名空间边界的“呼吸区”。函数/类实现内部各自的空行规则不受此约束影响。
* **块作用域规范**：流程控制语句（如 `if`,  `for`,  `while`）后的执行体**必须使用大括号 `{}` 包裹**，即使只有一行代码。严禁编写单行紧凑代码（如 `if (!ptr) return;`）。

## 3. 编译标准与核心范式

* **语言标准**：本项目当前锁定 **C++17**（这是本项目的当前选择，并非脚手架的固定要求；如实际项目采用其他标准，请直接修改本行，并同步检查下文涉及具体版本特性的条款是否需要调整）。除非本行另有约定，不得使用超出所锁定标准的语言特性。
* **资源管理**：严格遵守 RAII 原则，全面禁用裸指针和手动 `new/delete`，杜绝内存泄漏。优先使用按值传递、引用传递和智能指针。
* **性能优化与内存控制**：要求尽量减少运行时的内存动态分配。在可以确定数据规模（如矩阵大小）的前提下，尽量避免使用 `std::map`，且严禁使用没有提前调用 `reserve` 预分配内存的 `std::vector`。
* **编译期计算 (Compile-Time Evaluation)**：涉及到可以在编译期计算的热点函数（Hot Paths），必须尽量使用 `constexpr` 提前计算好，将运行时开销极致转移至编译阶段。
* **泛型与移动语义**：在模板编程中，必须熟练使用转发引用 (`T&&`) 配合 `std::forward` 实现完美转发，以及使用 `std::move` 消除不必要的拷贝。

## 4. 命名规范 (Repository Specific)

必须与现有代码库的命名习惯保持绝对一致，严禁引入未经批准的缩写（例如严禁将 cell 缩写为 c）：

* **命名空间 (Namespaces)**：小写下划线（如 `custom_cont`、`test_d_ary_heap`）。
* **类与结构体 (Classes/Structs)**：大驼峰/PascalCase（如 `DAryHeap`,  `PriQueue`,  `MyNode`）。
* **模板参数 (Template Parameters)**：大驼峰。尽量单字使用 `T`；在一个类型不够区分时，**必须以 `T` 开头**（如 `TNode`,  `TPri`,  `THash`）。
* **静态成员变量和编译期常量**：全大写加下划线/MACRO_CASE（如 `STATIC_PARAM`, `MAX_BUFFER_SIZE`）。
* **静态函数 (Static Functions)**：大驼峰/PascalCase（如 `BuildHeap`, `GetInstance`）。
* **成员函数 (Member Functions)**：小驼峰/camelCase（如 `buildHeap`,  `isLeafNode`,  `popAndReturn`）。
* **局部变量与参数 (Local Variables/Parameters)**：小写下划线/snake_case（如 `node_pos`,  `cmp_func`）。
* **内部成员变量 (Protected/Private Member Variables)**：小写下划线且**必须以单下划线结尾**（如 `d_`,  `cmp_func_`,  `size_`,  `nodes_`）。
* **枚举 (Enums)**：枚举类名称大驼峰，枚举值全大写加下划线（如 `PriQueueTyp::MIN_PRI_QUEUE`）。

## 5. 逻辑紧凑度与现代化实践

* **控制流扁平化与异常处理**：
  + 致力于降低圈复杂度，严禁深层嵌套的 `if/else`。
  + 必须强制使用“卫语句”(Guard Clauses) 处理异常或边缘情况，尽早返回（Happy Path 原则）。
  + 遇到非预期状态或越界访问，**优先抛出标准异常**（如 `std::out_of_range`,  `std::invalid_argument`,  `std::logic_error`），而不是返回错误码。
* **声明式与函数式风格**：
  + 摒弃命令式的过程代码。尽可能减少裸露的原始 `for` 循环。
  + 优先采用 Lambda 表达式将“判断策略”与“遍历机制”分离。
  + 优先使用基于范围的 for 循环 (`for (const auto& element : elements)`)。
* **数据构造优化**：优先使用初始化列表 (Initializer Lists) 直接填充容器，或使用 `emplace_back` 就地构造，杜绝产生冗余的临时变量。
* **现代 C++ 特性**：充分利用上方锁定标准所提供的现代特性消除样板代码，以 C++17 为例包括但不限于：
  + **结构化绑定** (Structured Binding)：如 `auto [node, key] = queue.topNode();`
  + **带初始化语句的 if**：缩小变量作用域。
  + **auto 类型推导**：配合 `decltype` 简化复杂类型声明。

## 6. 物理设计与文件包含 (Includes)

* **结构体与类型定义 (Structs & Types)**：`struct` 的定义尽量不要写在 `.cpp` 源文件中，而**必须优先放置在 `.h` 头文件中**。这样可以保证数据结构的可见性、跨文件复用性，并保持接口与实现的清晰分离。
* **相对路径原则**：本地头文件引用必须严格使用基于当前文件位置的**相对路径**。
  + **同级目录**：如果引用同文件夹下的头文件，直接使用当前层级。例如 `#include "a.h"`。
  + **跨级目录**：如果跨文件夹引用（例如从 `src/c.cpp` 引用 `include/b.h`），必须使用相对路径跳跃。例如 `#include "../include/b.h"` 或 `#include "../b.h"`。
* **标准库与第三方库**：系统或第三方库的头文件使用尖括号 `<>`（如 `#include <vector>`）。
